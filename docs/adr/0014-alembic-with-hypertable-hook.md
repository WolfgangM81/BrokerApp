# ADR-0014: Alembic + TimescaleDB via post-processing hook

- **Status:** Accepted
- **Date:** 2026-05-10 (recorded retroactively in Phase 8)

## Context

Alembic's `--autogenerate` produces clean diffs for ordinary tables but
has no knowledge of TimescaleDB-specific objects (hypertables,
continuous aggregates, retention policies). Without intervention it
would happily emit `CREATE TABLE market.bars (...)` and stop — the
table would exist but never become a hypertable.

The three workable options:

1. **Hand-write every migration.** Safe but tedious; trivial schema
   changes still need full hand-written revisions.
2. **Autogenerate everything, then post-process the revision script.**
   Alembic exposes `process_revision_directives`, which runs after the
   diff is computed. We can append `op.execute(...)` operations for
   any table that opts in to Timescale features via its `info` dict.
3. **External tooling** (sqitch, Liquibase, …). Adds a parallel
   migration runner; rejected.

## Decision

Use option (2). Two pieces of plumbing make it work:

### 2.1 Model opt-in via `__table_args__["info"]`

```python
class Bar(Base):
    __tablename__ = "bars"
    __table_args__ = (
        Index("ix_bars_asset_time", "asset_id", "time"),
        {
            "schema": "market",
            "info": {
                "timescale": {
                    "hypertable": {
                        "time_column_name": "time",
                        "chunk_time_interval": "INTERVAL '7 days'",
                    },
                },
            },
        },
    )
```

### 2.2 Hook in `migrations/env.py`

`process_revision_directives` walks `target_metadata.sorted_tables`,
finds the opted-in tables, and appends an
`op.execute("SELECT create_hypertable('market.bars', 'time', ...);")`
op to every autogenerated revision.

### 2.3 The metadata-population gotcha

`target_metadata = brokerapp_db.base.metadata` only knows about tables
that have actually been _defined_. The model module must therefore be
imported as a side effect _before_ the directive hook runs. We do this
explicitly in `env.py`:

```python
from brokerapp_db import models as _models  # noqa: F401
```

Without this line, autogenerate sees an empty MetaData and proposes
dropping every existing table — a footgun we hit in Phase 8.

### 2.4 The initial bootstrap

The 7-day chunk for `market.bars` and the extension+schema bootstrap
live in the **hand-written** `0001_initial_schema` revision. Subsequent
migrations rely on the autogenerate + hook combination.

## Consequences

**+** Day-to-day schema changes are still `alembic revision
       --autogenerate` followed by a quick review.
**+** Hypertable / continuous-aggregate ops are visible in the
reviewable revision script — not hidden behind opaque tooling.
**+** Adding a new hypertable is two lines on the model, zero
hand-written migration code.
**−** Reviewers must know that the `info["timescale"]` block is
load-bearing; we cover it here and in `env.py`.
**−** The hook is repo-specific and a little fragile. A version-pin on
Alembic in `pyproject.toml` plus the integration test
(`services/db/tests/test_integration.py::test_bars_is_hypertable`)
guard against regressions.
